# 独立开发（全栈\+私活）Git代码管理指南（可下载/一键复制）

适用场景：独立开发（前端\+全栈）、接私活（小程序\+后台管理系统），单人负责前后端，追求高效、简洁、可追溯，无需复杂配置，兼顾代码安全与交付便捷性

核心原则：工具轻量化、工作流极简、操作无冗余，适配单人开发节奏，同时满足私活交付的代码追溯、版本回滚需求

# 一、适合独立开发的Git代码管理工具推荐（优先选1个即可）

核心需求：免费/低成本、操作简单、支持私有仓库（私活代码需保密）、适配小程序\+后台项目，无需复杂团队协作功能，推荐3个最适配的工具，按优先级排序：

## 1\. 首选：Gitee（码云）

### 核心优势（完美适配独立私活开发）

- 完全免费：个人用户可创建**无限个私有仓库**，无容量限制，无需付费（私活代码保密关键）；

- 国内访问快：无需科学上网，提交/拉取代码速度快，适配小程序、后台项目（避免因网络问题影响开发效率）；

- 操作简单：界面和GitHub基本一致，上手无门槛，支持Web端直接查看、编辑代码，方便临时修改；

- 适配私活交付：支持生成仓库访问链接（可设置临时权限），方便给甲方演示代码、交付源码，无需额外部署；

- 附加功能实用：支持分支管理、标签（版本）管理、代码对比、历史记录回溯，满足独立开发的所有核心需求，还支持关联微信、快捷登录。

### 使用建议

- 注册个人账号，创建私有仓库（勾选“私有”，避免代码泄露），仓库命名规范：`project-小程序名称-后台`（如`project-mall-wechat-miniprogram-admin`）；

- 小程序和后台管理系统，建议**分开创建2个仓库**（避免代码混乱，交付时可分别提供源码，也可创建1个仓库，按目录区分：/miniprogram 和 /admin）；

- 开启仓库保护：设置仓库为“私有”，禁止陌生人访问，交付时可临时添加甲方账号为“只读”权限，交付完成后移除。

## 补充：Gitee新建仓库0\-1完整流程（从注册到关联本地）

适配独立开发，全程可视化操作，无需复杂命令，一步到位，确保仓库配置符合私活开发需求（以创建小程序项目仓库为例）

### 步骤1：Gitee账号注册与登录（首次使用）

1. 打开Gitee官网（https://gitee\.com/），点击右上角「注册」，选择「个人注册」；

2. 填写注册信息：用户名（建议用真实姓名/常用昵称，便于甲方识别）、手机号、验证码、密码，完成注册；

3. 注册完成后，点击右上角「登录」，输入账号密码，登录Gitee（可勾选“记住登录状态”，方便后续操作）；

4. 完善个人信息（可选）：点击头像→「个人设置」，上传头像、填写个人简介，提升账号可信度（交付时甲方可查看）。

### 步骤2：新建私有仓库（核心步骤）

1. 登录后，点击右上角「\+」号→「新建仓库」，进入仓库创建页面；

2. 填写仓库基础信息（严格按以下规范，避免后续麻烦）：

3. 仓库名称：规范命名，格式为「project\-项目类型\-项目名称」（如`project-miniprogram-mall`，小程序商城项目）；

4. 路径：默认与仓库名称一致，无需修改（便于记忆和访问）；

5. 仓库介绍：简单填写项目用途（如“小程序商城\+后台管理系统，私活项目”），方便后续自己追溯和甲方查看；

6. 仓库类型：**必须勾选「私有」**（关键！私活代码保密，禁止公开）；

7. 初始化仓库：勾选「初始化README文件」（便于后续添加项目说明），其他选项（如\.gitignore、许可证）暂不勾选（后续手动添加更灵活）；

8. 分支模型：选择「默认分支模型」（main分支作为默认分支，后续手动创建develop分支）。

9. 点击「创建仓库」，完成私有仓库创建，此时仓库默认只有main分支和README\.md文件。

### 步骤3：仓库基础配置（适配独立开发）

1. 进入新建的仓库页面，点击「设置」（仓库右上角），进入仓库设置页面；

2. 配置分支保护（防止误操作）：

3. 点击左侧「分支管理」→「分支保护」，点击「添加保护规则」；

4. 分支名称：填写「main」，勾选「禁止强制推送」「禁止删除此分支」，「允许推送」选择「仅自己」，「允许合并」选择「仅自己」，点击「确定」；

5. 重复上述操作，添加「develop」分支的保护规则（后续创建develop分支后配置），规则与main分支一致，确保开发分支安全。

6. 配置仓库权限（交付准备）：

7. 点击左侧「成员管理」→「添加成员」，输入甲方Gitee账号/手机号，选择「只读」权限（仅能查看代码，无法修改），点击「添加」；

8. 交付完成后，可在此页面移除甲方账号，避免后续代码泄露或误操作。

### 步骤4：关联本地项目（完成0\-1闭环）

```bash
# 1. 本地创建项目文件夹（如project-miniprogram-mall），进入文件夹
mkdir project-miniprogram-mall
cd project-miniprogram-mall

# 2. 初始化本地Git仓库
git init

# 3. 关联Gitee远程仓库（复制仓库地址，替换下方链接）
# 仓库地址获取：Gitee仓库页面 → 点击「克隆/下载」→ 复制HTTPS地址（无需配置SSH，更简单）
git remote add origin https://gitee.com/你的Gitee账号/project-miniprogram-mall.git

# 4. 拉取远程仓库的README文件（同步远程仓库内容）
git pull origin main

# 5. 创建develop分支（日常开发分支），并推送远程
git checkout -b develop
git push -u origin develop

# 6. 提交本地初始代码（如小程序基础框架），完成关联
git add .
git commit -m "init: 初始化小程序项目，关联Gitee仓库"
git push origin develop
```

至此，Gitee仓库从注册、创建、配置到关联本地，全程完成，可直接开始日常开发。

## 2\. 备选：GitHub（需科学上网）

### 核心优势

- 全球通用：知名度高，若后续接海外私活、或需要展示个人项目 portfolio，GitHub 更有优势；

- 功能完善：分支、标签、PR（合并请求）、代码审查功能成熟，适合长期沉淀项目；

- 免费私有仓库：个人用户可创建无限个私有仓库，容量足够独立开发使用。

### 不足

- 国内访问慢，需科学上网，提交代码偶尔卡顿，影响开发效率；

- 给国内甲方交付源码时，甲方可能无法正常访问，需额外打包源码发送。

## 3\. 备选：GitLab（本地部署/云版）

### 核心优势

- 完全可控：本地部署版可搭建在自己的服务器，代码完全私有，适合对代码安全要求极高的私活；

- 功能强大：支持完整的分支管理、CI/CD（可自动部署测试环境），适合长期多项目管理。

### 不足

- 门槛高：本地部署需要配置服务器，维护成本高，单人开发没必要；

- 云版免费额度有限，超出需付费，性价比不如Gitee。

### 工具最终推荐

优先选 **Gitee**，无需科学上网、免费私有仓库、操作简单，完美适配国内独立开发接私活的场景；若有海外需求，可搭配GitHub使用（国内用Gitee，海外用GitHub同步）。

# 二、适合独立开发（全栈\+私活）的Git工作流（极简高效，单人可执行）

核心逻辑：放弃复杂分支，仅保留3种分支，兼顾开发效率、版本追溯、交付便捷性，避免冗余操作，适配单人前后端开发节奏（小程序\+后台可共用一套工作流）。

## 1\. 分支规范（仅3种，极简无冗余）

|分支名称|核心作用|使用场景|
|---|---|---|
|main|生产环境/交付版本分支，仅存放可交付、稳定的代码|项目交付、上线后，代码固定在该分支，禁止随意修改|
|develop|日常开发分支，前后端开发、联调、自测都在该分支|单人开发的核心分支，所有功能开发、BUG修复都先在这进行|
|feature/xxx|临时功能分支（可选），用于开发独立功能/修复紧急BUG|开发复杂功能（如支付模块）、或修复线上BUG时，避免影响develop分支|

## 2\. 完整操作流程（可直接复制命令执行，适配Gitee）

### 步骤1：初始化仓库（项目开始前，仅执行1次）

```bash
# 1. 先在Gitee创建私有仓库（如project-mall-miniprogram），复制仓库地址
# 2. 本地初始化项目，关联远程仓库
mkdir project-mall-miniprogram  # 创建项目文件夹
cd project-mall-miniprogram     # 进入文件夹
git init                         # 初始化本地Git仓库

# 3. 关联Gitee远程仓库（替换为你的仓库地址）
git remote add origin https://gitee.com/你的账号/project-mall-miniprogram.git

# 4. 创建并切换到develop分支（日常开发分支）
git checkout -b develop

# 5. 提交初始文件（如README、项目初始化代码）
git add .
git commit -m "init: 项目初始化，创建小程序基础框架"

# 6. 推送到远程仓库（首次推送，后续无需重复）
git push -u origin develop

# 7. 创建main分支（交付/上线分支），并推送远程
git checkout -b main
git push -u origin main
```

### 步骤2：日常开发操作（前后端通用，每日执行）

```bash
# 1. 切换到develop分支，拉取远程最新代码（避免本地代码落后，单人开发也需执行，防止误操作）
git checkout develop
git pull origin develop

# 2. 开发功能/编写代码（小程序/后台），完成后暂存代码
git add .  # 暂存所有修改（或指定文件：git add src/pages/index/index.vue）

# 3. 提交代码（规范提交，方便后续追溯，无需复杂格式）
# 提交格式：类型: 描述（如feat: 新增小程序首页、fix: 修复后台登录BUG、refactor: 优化接口逻辑）
git commit -m "feat: 新增小程序商品列表页面，对接后台商品接口"

# 4. 推送代码到远程develop分支（防止代码丢失，每日至少推送1次）
git push origin develop
```

### 步骤3：复杂功能开发（可选，如支付、登录模块）

若开发复杂功能，可创建临时feature分支，避免影响develop分支的稳定

```bash
# 1. 从develop分支创建feature分支（命名规范：feature/功能名）
git checkout develop
git pull origin develop
git checkout -b feature/pay-module

# 2. 在feature分支开发功能，提交推送
git add .
git commit -m "feat: 完成小程序支付模块开发，对接支付接口"
git push origin feature/pay-module

# 3. 功能开发完成、自测通过后，合并到develop分支
git checkout develop
git merge feature/pay-module
git push origin develop

# 4. 合并完成后，删除临时feature分支（清理分支，避免冗余）
git push origin --delete feature/pay-module
```

### 步骤4：项目交付/上线（核心步骤，确保交付代码稳定）

```bash
# 1. 确认develop分支所有功能开发完成、自测通过，无BUG
git checkout develop
git pull origin develop  # 确保是最新代码

# 2. 合并到main分支（交付/上线分支）
git checkout main
git merge develop

# 3. 推送main分支到远程，标记版本标签（关键：方便交付追溯、后续回滚）
git push origin main

# 4. 打版本标签（命名规范：v1.0.0，按交付版本递增，如v1.0.0、v1.0.1）
git tag -a v1.0.0 -m "交付版本v1.0.0：完成小程序+后台基础功能，可交付甲方"
git push origin v1.0.0

# 5. 交付甲方：给甲方提供Gitee仓库只读权限，或打包main分支代码（git archive -o 项目名称-v1.0.0.zip main）
```

### 步骤5：交付后BUG修复（甲方反馈问题）

```bash
# 1. 从main分支创建临时修复分支（或直接在develop分支修复，单人开发可简化）
git checkout main
git pull origin main
git checkout -b feature/fix-admin-login

# 2. 修复BUG，提交推送
git add .
git commit -m "fix: 修复后台登录页面验证码失效问题（甲方反馈）"
git push origin feature/fix-admin-login

# 3. 合并到develop分支，自测通过
git checkout develop
git merge feature/fix-admin-login
git push origin develop

# 4. 合并到main分支，更新版本标签，重新交付
git checkout main
git merge feature/fix-admin-login
git push origin main

# 5. 更新版本标签（递增版本号）
git tag -a v1.0.1 -m "修复版本v1.0.1：修复甲方反馈的后台登录验证码BUG"
git push origin v1.0.1

# 6. 删除临时修复分支
git push origin --delete feature/fix-admin-login
```

### 步骤6：项目归档（交付完成后）

```bash
# 1. 确认main和develop分支代码一致，标记最终交付标签
git checkout main
git pull origin main
git checkout develop
git merge main
git push origin develop

# 2. 备份代码：将main分支代码打包，保存到本地（防止远程仓库出现问题）
git archive -o 项目名称-最终交付版.zip main

# 3. 后续维护：若甲方需要新增功能，重复步骤2-4，递增版本号（v1.1.0）
```

# 三、补充配置（前端专属\+Gitee CI/CD）

## 1\. 前端项目专属 Git 提交规范校验配置（\.commitlintrc\.js \+ \.husky）

适配前端项目（小程序、Vue/React后台），强制规范提交信息，避免杂乱提交，方便后续追溯，无需手动校验，提交时自动拦截不规范信息。

### 步骤1：安装依赖（项目根目录执行）

```bash
# 初始化package.json（若未初始化）
npm init -y

# 安装提交校验相关依赖（开发依赖）
npm install husky @commitlint/cli @commitlint/config-conventional -D

# 安装commitizen（可选，提供交互式提交，更便捷）
npm install commitizen cz-conventional-changelog -D
```

### 步骤2：创建配置文件（项目根目录）

#### （1）\.commitlintrc\.js（提交校验规则配置）

```javascript
// .commitlintrc.js
module.exports = {
  // 继承默认的提交规范
  extends: ['@commitlint/config-conventional'],
  // 自定义提交规则（适配前端+私活开发，简化规则，不冗余）
  rules: {
    // type（提交类型）必须存在，且只能是以下值
    'type-enum': [
      2, // 0=禁用，1=警告，2=错误（强制校验）
      'always',
      [
        'init',    // 初始化项目
        'feat',    // 新增功能（如新增页面、接口）
        'fix',     // 修复BUG
        'refactor',// 代码重构（不新增功能、不修复BUG）
        'docs',    // 文档更新（如README、接口文档）
        'style',   // 代码格式调整（不影响逻辑，如缩进、空格）
        'test',    // 测试相关（如新增测试用例）
        'chore'    // 构建/依赖更新（如npm install、配置修改）
      ]
    ],
    // type（提交类型）不能为空
    'type-empty': [2, 'never'],
    // subject（提交描述）不能为空，且长度不超过100字符
    'subject-empty': [2, 'never'],
    'subject-max-length': [1, 'always', 100],
    // 提交描述首字母小写（可选，统一格式）
    'subject-case': [1, 'always', 'lower-case']
  }
}
```

#### （2）配置husky（提交拦截触发）

```bash
# 初始化husky（生成.husky文件夹）
npx husky install

# 设置husky自动启用（每次npm install后自动启用）
npm set-script prepare "husky install"
npx husky add .husky/prepare "husky install"

# 添加commit-msg钩子（提交信息校验）
npx husky add .husky/commit-msg 'npx --no -- commitlint --edit $1'

# （可选）添加pre-commit钩子（提交前校验代码格式，如ESLint）
# 若项目有ESLint，可添加此钩子，避免格式错误提交
npx husky add .husky/pre-commit "npx eslint . --ext .js,.vue,.jsx,.ts,.tsx"
```

#### （3）配置交互式提交（可选，更便捷）

```javascript
// package.json 中添加配置
{
  "scripts": {
    "commit": "git-cz"
  },
  "config": {
    "commitizen": {
      "path": "cz-conventional-changelog"
    }
  }
}
```

### 使用说明

- 常规提交：git commit \-m "feat: 新增小程序购物车页面"（需符合type规范，否则会被拦截）；

- 交互式提交：npm run commit，按提示选择提交类型、输入描述，自动生成规范提交信息；

- 若提交信息不规范（如无type、描述为空），husky会拦截提交，提示修改后重新提交。

## 2\. Gitee CI/CD 触发规则（自动部署开发/测试环境）

适配独立开发，无需手动部署，合并代码后自动部署到开发/测试环境（以前端项目为例，后台项目可参考此逻辑），节省部署时间，避免手动操作失误。

### 前置准备

- 拥有服务器（云服务器即可，如阿里云、腾讯云，需开放80/443端口）；

- 服务器安装Nginx（用于部署前端项目，静态文件托管）；

- Gitee仓库开启CI/CD功能（默认开启，无需额外配置）；

- 获取服务器SSH密钥（用于Gitee CI/CD连接服务器）。

### 步骤1：配置服务器SSH密钥（Gitee关联）

```bash
# 1. 登录服务器（通过Xshell、FinalShell等工具）
# 2. 生成SSH密钥（无需设置密码，直接回车）
ssh-keygen -t rsa -C "你的Gitee邮箱"

# 3. 查看公钥内容（复制全部内容）
cat ~/.ssh/id_rsa.pub

# 4. Gitee关联公钥：
# 登录Gitee → 头像→个人设置→SSH公钥 → 粘贴服务器公钥，填写标题（如“部署服务器”），点击确定
```

### 步骤2：创建Gitee CI/CD配置文件（\.gitlab\-ci\.yml）

项目根目录创建`.gitlab-ci.yml`文件（Gitee CI/CD兼容GitLab的配置格式），复制以下内容，替换对应参数：

```yaml
# .gitlab-ci.yml（Gitee CI/CD配置，适配前端项目自动部署）
# 定义 stages（流程阶段：安装依赖→构建→部署）
stages:
  - install
  - build
  - deploy

# 环境变量（替换为你的服务器信息）
variables:
  # 服务器IP地址
  SERVER_IP: "你的服务器IP"
  # 服务器登录用户名（默认root）
  SERVER_USER: "root"
  # 服务器部署目录（Nginx配置的静态文件目录，如/usr/share/nginx/html/miniprogram）
  DEPLOY_DIR: "/usr/share/nginx/html/miniprogram"

# 1. 安装依赖（仅在develop分支触发，开发环境部署）
install:
  stage: install
  tags:
    - gitee
  only:
    - develop  # 仅监听develop分支
  script:
    - npm install  # 安装项目依赖

# 2. 构建项目（开发环境，不压缩，便于调试）
build:
  stage: build
  tags:
    - gitee
  only:
    - develop
  script:
    - npm run build:dev  # 替换为你的开发环境构建命令（如vue项目：npm run build:dev）
  artifacts:
    paths:
      - dist/  # 构建后的文件目录（替换为你的项目构建目录）
  dependencies:
    - install

# 3. 部署到开发环境（合并到develop分支后自动部署）
deploy-dev:
  stage: deploy
  tags:
    - gitee
  only:
    - develop
  script:
    # 连接服务器，删除原有部署文件，上传新构建文件
    - ssh $SERVER_USER@$SERVER_IP "rm -rf $DEPLOY_DIR/*"
    - scp -r dist/* $SERVER_USER@$SERVER_IP:$DEPLOY_DIR
    # 重启Nginx（可选，确保配置生效）
    - ssh $SERVER_USER@$SERVER_IP "systemctl restart nginx"
  dependencies:
    - build

# 4. 测试环境部署（合并到main分支后自动部署，可选）
deploy-test:
  stage: deploy
  tags:
    - gitee
  only:
    - main  # 监听main分支，合并后自动部署到测试环境
  script:
    - npm install
    - npm run build:test  # 测试环境构建命令（压缩代码，模拟生产）
    - ssh $SERVER_USER@$SERVER_IP "rm -rf /usr/share/nginx/html/test-miniprogram/*"
    - scp -r dist/* $SERVER_USER@$SERVER_IP:/usr/share/nginx/html/test-miniprogram
    - ssh $SERVER_USER@$SERVER_IP "systemctl restart nginx"
  when: manual  # 手动触发（可选，避免误合并导致部署）
```

### 关键配置说明

- 触发规则：develop分支合并后，自动执行「安装依赖→构建→部署开发环境」；main分支合并后，可手动触发测试环境部署；

- 替换参数：SERVER\_IP（服务器公网IP）、SERVER\_USER（服务器登录用户名）、DEPLOY\_DIR（开发环境部署目录），需根据自己的服务器配置修改；

- 构建命令：替换为你的项目构建命令（如Vue项目：开发环境npm run build:dev，测试环境npm run build:test；小程序项目可根据打包命令调整）；

- Nginx配置：确保部署目录与Nginx配置一致，避免部署后无法访问（Nginx配置示例见下文）。

### 补充：Nginx配置示例（前端项目）

```nginx
# 登录服务器，编辑Nginx配置文件
vim /etc/nginx/conf.d/miniprogram.conf

# 粘贴以下配置（替换部署目录和域名）
server {
    listen 80;
    server_name dev-mall.xxx.com;  # 开发环境域名（可选，无域名可直接用IP）
    root /usr/share/nginx/html/miniprogram;  # 与CI/CD配置的DEPLOY_DIR一致
    index index.html index.htm;

    # 解决前端路由刷新404问题（SPA项目必备）
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 禁止访问隐藏文件
    location ~ /\. {
        deny all;
    }
}

# 保存配置，重启Nginx
systemctl restart nginx
```

### CI/CD使用说明

- 提交代码：将配置文件提交到Gitee仓库（develop分支）；

- 触发部署：当合并代码到develop分支后，Gitee会自动执行CI/CD流程，可在仓库「CI/CD」→「流水线」查看部署进度；

- 异常排查：若部署失败，查看流水线日志，常见问题：服务器SSH连接失败、部署目录权限不足、构建命令错误，对应修改即可。

# 四、遗漏点\&注意事项（独立开发接私活必看，避免踩坑）

## 1\. 代码管理工具相关注意事项

- 仓库隐私：必须设置为**私有仓库**，禁止公开（私活代码涉及甲方商业信息，公开可能导致纠纷）；

- 权限管理：交付时给甲方“只读”权限，交付完成后及时移除，避免甲方误操作修改代码；

- 备份策略：除了远程仓库，本地需定期备份代码（每周1次），同时可将关键版本（交付版）打包保存，防止远程仓库异常（如账号被盗、仓库误删）；

- 忽略文件：必须创建`.gitignore`文件，忽略无用文件（如node\_modules、dist、小程序开发工具生成的临时文件、IDE配置文件），避免提交冗余文件，减小仓库体积。

推荐\.gitignore内容（小程序\+后台通用）：

```plaintext
# 前端通用
node_modules/
dist/
build/
.env.local
.env.development.local
.env.production.local

# 小程序专用
miniprogram_npm/
unpackage/
project.config.json.backup
*.sublime-project
*.sublime-workspace

# 后台通用（如Node.js/Python）
venv/
node_modules/
*.log
.DS_Store
.idea/
.vscode/
*.pyc
__pycache__/

# 打包文件
*.zip
*.rar
```

## 2\. Git工作流相关注意事项

- 禁止直接修改main分支：main分支仅用于交付/上线，所有开发、修复都在develop或feature分支进行，避免误操作导致交付代码异常；

- 提交规范：即使是单人开发，也要规范提交信息（如feat/fix/refactor），方便后续追溯问题、回滚版本（比如甲方反馈某个功能有问题，可快速找到对应提交记录）；

- 版本标签必打：每次交付、修复后，必须给main分支打版本标签，标签命名规范（v1\.0\.0），这是交付凭证，也方便后续维护时快速回滚到对应版本；

- 避免分支冗余：单人开发无需创建过多分支，feature分支仅用于复杂功能/紧急修复，用完及时删除，保持分支清晰。

## 3\. 独立开发接私活额外注意点（易遗漏）

- 代码版权：在仓库根目录创建`LICENSE`文件，明确代码版权归属（如“本项目代码版权归开发者所有，仅授权甲方使用，禁止二次传播”），避免后续版权纠纷；

- 敏感信息处理：严禁将敏感信息（如数据库密码、接口密钥、小程序AppID、支付密钥）提交到Git仓库，需使用环境变量（\.env文件）管理，且\.env文件必须加入\.gitignore；

- 交付规范：交付时，除了提供Git仓库地址/打包源码，还需提供版本说明（如当前版本实现的功能、已知问题、后续维护注意事项），提升专业度；

- 回滚操作：若交付后发现严重BUG，可快速回滚到上一稳定版本（命令：git checkout main \&\& git reset \-\-hard v1\.0\.0 \&\& git push origin main \-\-force\-with\-lease），操作前务必确认，避免数据丢失；

- 多项目管理：若同时接多个私活，建议给每个项目创建独立的Git仓库，命名规范统一（如project\-甲方名称\-项目类型），避免项目代码混淆。

## 4\. Cursor/Trae AI开发专属注意事项（针对乱改代码隐患）

全程使用Cursor、Trae开发时，核心规避“AI乱改代码”隐患，同时兼顾开发效率与代码安全，适配独立开发\+私活场景，补充以下专属注意点：

- AI操作权限管控：关闭Cursor/Trae的「自动保存修改」「自动优化代码」功能，所有AI生成、修改的代码，必须手动确认后再保存，禁止AI后台自动篡改本地代码；

- 代码修改留痕管控：使用AI生成/修改代码前，先执行git commit提交当前稳定版本（备注“AI修改前\-xxx功能”），若AI乱改代码，可快速通过git回滚到修改前状态，避免代码丢失；

- AI生成代码校验：AI生成的代码（尤其是复杂逻辑、接口对接、工具类代码），必须逐行校验，重点检查语法错误、逻辑漏洞、变量命名一致性，禁止直接复制粘贴后不校验就提交；

- 本地代码保护：禁止Cursor/Trae关联远程仓库直接推送代码，所有AI修改后的代码，先在本地自测通过，再手动执行git add、git commit、git push流程，避免AI误推错误代码到远程；

- 临时文件隔离：AI生成的临时代码片段、测试代码，单独创建temp文件夹存放，且将temp文件夹加入\.gitignore，禁止提交到远程仓库，避免冗余代码与错误代码混入正式分支；

- 版本对比校验：若怀疑AI乱改代码，可通过Git的git diff命令（对比当前代码与上一版本差异），或Cursor/Trae的代码历史记录，快速定位AI修改的内容，及时还原错误修改；

- 敏感代码防护：编写数据库连接、密钥配置、支付接口等敏感代码时，临时关闭AI辅助功能，避免AI误修改敏感信息，或生成包含敏感信息的冗余代码；

- IDE配置锁定：固定Cursor/Trae的代码格式、缩进、命名规范，关闭AI自动调整代码格式的功能，避免AI频繁修改代码格式（非逻辑修改），导致代码混乱、提交记录冗余；

- 多版本备份：使用AI开发期间，每日至少提交2次代码（上午、下午各1次），关键功能开发完成后立即打临时标签（如v0\.1\.0\-ai），若AI乱改无法还原，可通过标签回滚到稳定版本；

- AI提示词规范：给AI下达开发指令时，明确要求“不修改已有正确代码、不新增冗余逻辑、不篡改变量/函数命名”，减少AI乱改代码的概率；若出现AI乱改，及时调整提示词并重启IDE。

## 5\. AI辅助开发 + Feature分支工作流（专属推荐）

适用场景：使用AI（Cursor/Trae/GitHub Copilot）辅助编写代码，你负责审查和把控质量，AI可能改错代码、产生无效代码，需要一套安全高效的分支策略来隔离风险。

### 为什么仅靠 Git 历史回滚不够？

| 方案 | 问题 |
|---|---|
| AI 改错后在 develop 上回滚 | 回滚意味着连同其它正常功能一起丢掉；`git reset --hard` 不可逆，操作失误代码直接丢失 |
| AI 改动混在 10 个文件中 | 无法单独验证某个功能是否正常，审查效率极低 |
| 事后才发现 bug | develop 已被污染，其它功能可能已基于错误代码继续开发 |

### 分支策略（main → develop → feature/xxx）

```
main        ───●──────────────────────●──────  （唯一稳定版本，仅交付/上线用）
                  \                  /
develop     ───●──●──●───────────●───●───  （开发集成，始终可运行）
                  \      \     /
feature/reg    ───●──●───●───  （AI 写注册功能，完成→合并→删除）
                       \
feature/oauth       ───●──●──● （AI 写 OAuth，完成→合并→删除）
```

- **main**：仅存放可交付的稳定代码，禁止直接修改
- **develop**：本地/测试环境运行的开发分支，保持随时可用
- **feature/xxx**：每个独立功能一条临时分支，AI 在上面写，你审查通过后合并到 develop 并立即删除

### 完整操作流程（AI 辅助开发，每个功能执行一次）

以开发「登录」功能为例，它内部包含多个小功能点：邮箱登录接口 → 表单校验 → 密码加密 → 登录失败限制。

```bash
# ========== 步骤1：开始新功能 ==========
# 从 develop 拉一条临时分支（命名规则：feature/功能名）
git checkout develop
git pull origin develop          # 确保本地 develop 最新
git checkout -b feature/login     # 创建并切换到 feature 分支

# ========== 步骤2：在 feature 分支上，小块 commit + 推远程备份 ==========
# AI 每完成一个小功能点，就 commit 一次，所有 commit 都在当前 feature 分支内
git add .
git commit -m "feat: 实现邮箱密码登录接口"
git push origin feature/login    # 备份到远程 feature 分支

# 继续开发下一个小功能...
git add .
git commit -m "feat: 添加登录表单 Zod 校验"
git push origin feature/login    # 再次备份

git add .
git commit -m "feat: 接入 bcrypt 密码加密"
git push origin feature/login

git add .
git commit -m "feat: 增加登录失败次数限制"
git push origin feature/login

# ========== 步骤3：整个功能点全部完成、自测通过后，合并到 develop ==========
git checkout develop
git pull origin develop          # 合并前先拉最新
git merge feature/login           # 一次性将所有 commit 合并到 develop
git push origin develop           # 推送 develop 到远程

# ========== 步骤4：删除临时分支（保持仓库整洁）==========
git branch -d feature/login               # 删除本地分支
git push origin --delete feature/login    # 删除远程分支
```

> **关键理解**：步骤 2 中的多次 commit 和 push 都只在 `feature/login` 分支内，develop 完全不受影响。只有当你确认整个功能开发完成、自测通过后，才执行步骤 3 一次性合并到 develop。

### Feature 分支上的回滚操作（AI 改错代码的应对）

feature 分支是隔离的，回滚非常安全，完全不影响 develop。

**场景 1：上一个 commit 改错了，想撤销掉**

```bash
# 撤销最近 1 次 commit，改动保留在工作区（可以修改后重新提交）
git reset --soft HEAD~1

# 或者连改动一起丢掉（彻底不要了）
git reset --hard HEAD~1
git push -f origin feature/login  # 同步强制更新远程 feature 分支
```

**场景 2：想回到今天上午的某个稳定状态**

```bash
git log --oneline                 # 先看提交历史，找到稳定版本的 commit ID
git reset --hard abc1234          # 回到那个版本，后面的改动全部丢弃
git push -f origin feature/login  # 同步远程
```

**场景 3：整个分支被 AI 改废了，不想修了**

```bash
git checkout develop
git branch -D feature/login       # 强制删除本地分支（注意大 D）
git push origin --delete feature/login  # 删除远程分支
git checkout -b feature/login     # 从 develop 重新拉一条干净的，重来
```

**场景 4：只想撤销某个文件的改动**

```bash
git checkout -- src/modules/auth/auth.controller.ts  # 单个文件恢复到最后一次 commit 的状态
```

### 需要拉取同事（或多个 feature）分支的代码？

```bash
# 先获取远程所有分支的最新信息
git fetch origin

# 方式1：把同事的整个 feature/oauth 分支合并到你当前分支
git merge origin/feature/oauth

# 方式2：只拉同事分支的几个特定文件（不影响其余代码）
git checkout origin/feature/oauth -- src/modules/auth/auth.service.ts
git checkout origin/feature/oauth -- src/modules/auth/auth.middleware.ts
git commit -m "合并 feature/oauth 中 auth 核心代码"
```

### AI 辅助开发的日常节奏

> **核心区分**：`push origin feature/xxx` = 备份当前进度（随时做）；`merge + push origin develop` = 合并到主干（仅功能完成时做）

```
整天都在做 login 功能，当天没做完：

  上午 9:00
    git checkout develop && git pull origin develop
    git checkout -b feature/login
    AI 写代码，你审查
    10:30 小功能点①完成 → commit → push origin feature/login（备份①）

  下午 14:00
    小功能点②完成 → commit → push origin feature/login（备份②）
    15:00 小功能点③完成 → commit → push origin feature/login（备份③）
    16:00 还没做完，今天到此为止
    push origin feature/login（下班前最终备份）

  第二天继续：
    git checkout feature/login（直接切回 feature 分支继续写）
    小功能点④⑤完成，整个 login 功能自测通过
    此时才：git checkout develop → git merge feature/login → push origin develop
    然后删掉 feature/login

────────────────────────────────────

半天就做完的功能，当天合并 develop：

  上午 9:00
    git checkout -b feature/login
    小功能点①②完成 → commit → push origin feature/login

  下午 14:00
    整个 login 功能全部完成，自测通过
    git checkout develop && git pull origin develop
    git merge feature/login
    git push origin develop
    git branch -d feature/login（删本地）
    git push origin --delete feature/login（删远程）

────────────────────────────────────

下班前（每天必做）：

  1. 如果 feature 分支还没做完：push origin feature/xxx（备份进度）
  2. 如果已合并到 develop：push origin develop（确保远程最新）
  3. 每日至少推送 1-2 次，推到「当前工作的分支」，防止本地代码丢失
```

### 一句话记忆

**小 commit → 推 feature 分支备份；整个功能完成 → 联合并 develop → 删 feature。**

### 交付/上线前（合并到 main）

```bash
# 1. 确保 develop 稳定、自测通过
git checkout develop && git pull origin develop

# 2. 合并到 main
git checkout main && git pull origin main
git merge develop
git push origin main

# 3. 打版本标签
git tag -a v1.0.0 -m "正式版本 v1.0.0"
git push origin v1.0.0

# 4. 切回 develop 继续开发
git checkout develop
```

### 核心原则总结

- **隔离风险**：每次新功能拉独立的 feature 分支，AI 改废了直接删，不影响 develop
- **小块提交**：AI 每完成一个小功能就 commit 一次，不要攒到最后一起提交
- **审查后再合并**：绝不把未审查的 AI 代码直接合到 develop
- **用完即删**：feature 合到 develop 后立即删除，避免分支堆积
- **main 只做交付**：日常开发绝不碰 main，交付/上线时才合并

## 6\. 常用Git命令速查（独立开发高频使用，一键复制）

```bash
# 1. 查看当前分支
git branch

# 2. 切换分支
git checkout 分支名

# 3. 拉取远程分支最新代码
git pull origin 分支名

# 4. 推送本地分支到远程
git push origin 分支名

# 5. 合并分支（切换到目标分支后执行）
git merge 源分支名

# 6. 查看提交记录（简洁版）
git log --oneline

# 7. 打版本标签
git tag -a 标签名 -m "标签描述"

# 8. 推送标签到远程
git push origin 标签名

# 9. 回滚到指定版本（谨慎使用）
git reset --hard 标签名/提交ID

# 10. 打包当前分支代码
git archive -o 文件名.zip 分支名

# 11. 查看.gitignore忽略的文件
git status --ignored

# 12. 查看当前代码与上一版本差异（AI乱改代码时常用）
git diff HEAD^ HEAD
```
